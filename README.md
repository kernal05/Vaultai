# VaultAI

Personal portfolio project — an AI-assisted "status poster maker" (Crafto-inspired,
original templates/branding), built and operated the way an MNC platform team would:
isolated network, resource-capped containers, CI/CD with a security scan and an
approval gate, and scoped observability.

This stack is fully isolated from every other project on this host
(`hms-*`, `verifychain-*`, `crm_prod_setup-*`, `frappe_docker-*`, etc). It:

- runs on its own Docker network (`vaultai_net`)
- lives under its own directory (`/opt/vaultai`)
- has hard memory/CPU limits on every container
- has its own Jenkins folder + credential store
- never binds the database to a host port

## Layout

```
vaultai/
├── app/              # frontend (React/Vite poster maker) — drop status-craft source here
├── api/              # FastAPI service — AI captions, health, metrics
├── nginx/            # frontend nginx config (/healthz included)
├── monitoring/        # Prometheus scrape config, scoped to vaultai_net only
├── scripts/
│   ├── 00-bootstrap.sh   # run once: creates network + /opt/vaultai layout
│   ├── 01-deploy.sh      # build + up, with a pre-flight memory check
│   └── 99-rollback.sh    # roll back to a previous image tag
├── docker-compose.yml
├── Jenkinsfile
├── .env.example
└── .gitignore
```

## First-time setup on the server

```bash
# 1. Copy this project to the server
scp -r vaultai root@103.192.198.240:/opt/

# 2. SSH in and bootstrap
ssh root@103.192.198.240
cd /opt/vaultai
chmod +x scripts/*.sh
./scripts/00-bootstrap.sh

# 3. Create the dedicated non-root service user that will own/deploy this
./scripts/04-create-service-user.sh
# (save the printed private key into a Jenkins credential — see CI/CD section below)

# 4. Drop your existing status-craft React app source into app/
#    (package.json, src/, index.html, etc.)

# 5. Configure secrets
cp .env.example .env
nano .env   # set real POSTGRES_PASSWORD, GRAFANA_ADMIN_PASSWORD
chmod 600 .env

# 6. Lock the firewall to SSH-only (doesn't touch root/password auth)
./scripts/02-firewall-lockdown.sh

# 7. Hand ownership to the service user and do the first deploy as that user
chown -R vaultai:vaultai /opt/vaultai
sudo -u vaultai ./scripts/01-deploy.sh
```

## Access — locked to you only

Every port is bound to `127.0.0.1` in `docker-compose.yml`, so nothing here
is reachable from the public internet, full stop.

**On the "brothers with the same root password" situation** — one honest
technical fact first: file permissions cannot hide anything from someone who
has root, by definition. What actually protects this project is that
deployment never touches root at all:

- Jenkins runs as its own dedicated system user (see
  `scripts/04-create-service-user.sh`, creates a `vaultai` user)
- `/opt/vaultai` is owned by that user, `chmod 750` — not world-readable,
  not something a casual root login stumbles into
- `.env` is `chmod 600`
- The Jenkins deploy step authenticates with its own SSH key, generated by
  that script, never the shared root password
- Deploys are triggered by a GitHub webhook on `git push`, not manual SSH
  sessions — less reason for anyone to be in that directory by hand at all

This stops accidental or casual interference completely, and raises the bar
for deliberate interference to "someone consciously used root to override
another user's file permissions" — which is a very different, and noticeable,
action from what happens today. The only complete fix, if it ever becomes a
real problem, is rotating the root password so it's no longer shared — that's
optional and entirely your call; nothing here requires it.

Reach the running services yourself via SSH tunnel, from your own laptop:

```bash
./scripts/tunnel.sh
```

- Frontend: `http://localhost:8081`
- API: `http://localhost:8082/healthz`
- Prometheus: `http://localhost:9091`
- Grafana: `http://localhost:3001` (login admin / your GRAFANA_ADMIN_PASSWORD)

`01-deploy.sh` refuses to deploy if the host has under 800MB available, so a bad
deploy here can't push other projects into OOM.

## Real CI/CD flow (git → Jenkins → server)

This is the actual end-to-end pipeline, not a manual process:

1. You `git push` from your laptop to GitHub (`main` branch, or a feature
   branch + PR into `main`).
2. A GitHub webhook fires and triggers the Jenkins job automatically
   (`githubPush()` trigger in the `Jenkinsfile` — no polling, no manual "build now").
3. Jenkins (running as its own `jenkins` OS user, not root) checks out the repo,
   lints and builds the frontend, compiles the API, builds both Docker images.
4. Trivy scans both images for HIGH/CRITICAL CVEs (report-only until you baseline).
5. On `main`, images are pushed to GHCR.
6. Jenkins pauses for **manual approval** (the `input` step) — you click Deploy
   in the Jenkins UI.
7. Jenkins deploys over SSH as the dedicated `vaultai` user (its own key,
   `scripts/04-create-service-user.sh`), running `docker compose up -d` in
   `/opt/vaultai`.

### One-time setup for this flow

```bash
# On the server, as root (one-time):
./scripts/04-create-service-user.sh
# copy the printed private key contents into a Jenkins credential
# (folder: vaultai, kind: SSH Username with private key, id: vaultai-deploy-key)
```

In GitHub: repo Settings → Webhooks → Add webhook → point at
`http://<jenkins-host>/github-webhook/`, content type `application/json`,
event: `just the push event`.

In Jenkins: install the GitHub plugin, create the `vaultai` folder, add a
Multibranch Pipeline pointed at this repo, using this `Jenkinsfile`.


## Rollout order

1. Bootstrap network + directories (`00-bootstrap.sh`) — done before anything else.
2. Deploy frontend + api + db standalone, confirm `/healthz` on both.
3. Wire Jenkins folder + first green pipeline run.
4. Implement the first real AI feature in `api/main.py` (`/api/v1/caption` is a stub).
5. Point Prometheus/Grafana dashboards at the running services.
6. Add a domain + TLS (Caddy or Traefik) once you have one — swap `ports:` mappings
   for a reverse proxy at that point, everything else stays the same.
